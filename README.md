# Спортивный турнир

Сервис для проведения турниров. Пользователи собираются в команды, команды подают заявки на турнир,
организатор допускает команды и запускает турнир, после чего автоматически составляется график матчей.
Результаты матчей записываются, по ним строится турнирная таблица и определяется победитель.
Данные хранятся в PostgreSQL.

Лабораторная № 4 продолжает № 3. Java 21, Spring Boot, Spring Data JPA, PostgreSQL, Spring Security.

## Сущности

- Пользователь (`/api/users`): имя, email для входа, роль и состояние блокировки.
- Команда (`/api/teams`): название, капитан, состав (список игроков).
- Турнир (`/api/tournaments`): название, лимит команд, статус, победитель, дата завершения.
- Заявка команды (`/api/team-applications`): команда, турнир, статус допуска, время подачи.
- Матч (`/api/matches`): турнир, две команды, счёт, статус, время игры.

Связи: у команды один капитан и много игроков, один игрок может быть в нескольких командах.
Команда подаёт заявки на турниры, в турнире много матчей, в каждом матче две команды.

Для всех сущностей есть GET (список и по id), POST, PATCH и DELETE.

Статусы турнира: REGISTRATION → IN_PROGRESS → FINISHED.
Статусы заявки: PENDING, APPROVED, REJECTED, WITHDRAWN.
Статусы матча: SCHEDULED → FINISHED.

## Бизнес-операции

1. `POST /api/team-applications/{id}/approve`, допустить команду. Только пока идёт регистрация,
   если лимит турнира ещё не набран и в команде минимум 2 игрока.
2. `POST /api/tournaments/{id}/start`, начать турнир. Нужно минимум 2 допущенные команды.
   Заявки, которые так и не рассмотрели, отклоняются, и создаются матчи каждой команды с каждой.
3. `POST /api/matches/{id}/result`, записать результат матча (`score1`, `score2`). Только для несыгранного матча
   в идущем турнире, время игры ставит сервер.
4. `POST /api/team-applications/{id}/withdraw`, снять команду с идущего турнира. Все её несыгранные матчи
   засчитываются техническим поражением 0:3.
5. `POST /api/tournaments/{id}/finish`, завершить турнир. Только когда сыграны все матчи.
   Победителем становится лучшая команда по таблице (снятые команды не учитываются).

Дополнительно `GET /api/tournaments/{id}/standings` показывает турнирную таблицу: победа 3 очка, ничья 1,
при равенстве очков смотрится разница мячей.

Если операцию нельзя выполнить в текущем состоянии, возвращается 409.

Другие ограничения:
- статусы турнира и заявок через PATCH не меняются (кроме отклонения заявки), только операциями;
- после старта нельзя подать или удалить заявку и поменять лимит команд;
- после завершения турнира его матчи нельзя менять и удалять;
- при удалении капитана удаляется его команда, а у других команд он просто убирается из состава;
- при удалении команды удаляются её заявки и матчи, а если она была победителем, победитель очищается.

## Доступ к API

Вход через HTTP Basic: email и пароль. Пароли хранятся как BCrypt-хеши.
Регистрация создаёт PLAYER. Пароль: от 10 символов, заглавная и строчная буквы, цифра, без пробелов.
Email должен быть уникальным. Пользователь с enabled=false не может войти.

PLAYER читает команды, турниры и матчи, меняет свой профиль. Капитан управляет своей командой,
подаёт и удаляет её заявки до старта, снимает её с идущего турнира через withdraw.
ORGANIZER управляет всеми данными, допускает команды, начинает и завершает турнир, записывает результаты.

Начальная учётная запись организатора: organizer@tournament.local / Organize2026!.

## Запуск

1. В PostgreSQL под пользователем postgres выполнить скрипты из папки `db` по порядку:
   `1_create_db.sql` (в базе postgres, в pgAdmin по одной команде), затем `2_schema.sql` и `3_test_data.sql`
   (в базе tournament_db). Создастся база, таблицы, тестовые данные и пользователь `tournament_app`,
   у которого есть права только на чтение и изменение данных.
2. Для четвёртой лабы выполнить `db/4_security.sql` под postgres в базе tournament_db.
   Если база уже была создана в третьей лабе, достаточно только этого скрипта.
   Старые данные сохранятся. У старых пользователей пока нет паролей: их может задать организатор через PATCH.
3. Создать файл `.env` по примеру `.env` (адрес базы, логин, пароль).
4. Запустить `TournamentApplication`. Адрес http://localhost:8080; предыдущую версию на этом порту остановить.

Проверка входа в браузере: http://localhost:8080/api/account/me.

Запросы в `requests.http` выполнять сверху вниз. Сначала получается CSRF-токен, затем создаются игроки
и выполняется турнирный сценарий. Токен и id запоминаются скриптами ответов, cookie сохраняет HTTP-клиент.
В названиях запросов указан ожидаемый статус: 401 — ошибка входа, 403 — нет прав/CSRF, 409 — конфликт.
В `crud.http` — отдельные примеры всех CRUD-операций; его тоже выполнять по порядку.
